# Phase 0.5 报告：引文锚点命中率实验

**日期**: 2026-08-30
**实验对象**: `10.1109_tii.2020.2999571.pdf`，8 个 derived JSON（4 个 prompt × 2 个 model），对应 OCR 文本 `src/10.1109_tii.2020.2999571/10.1109_tii.2020.2999571.md`（141 段）
**核心问题**: 综合简报里的承重假设——"从逐字引文到 OCR 段落锚点"的确定性映射——在当前 litrev 提示词输出下能否成立？这是同行评审员标记的"最弱链接"，也是 `tech-debt-analyst` 的 #1 条件"提取时必须产出锚点"，这条在综合计划里被删掉了。

## 实验设计

四组子测试，共用一个匹配器（Phase 0 的 diff 逻辑原型）：

1. **正控制组**：取 OCR 原文前 14 个词作"逐字引文"，验证匹配器本身 + OCR 稳定性无 bug。
2. **当前提示词产物**：扫 8 个 derived JSON 的全部字符串字段，抽 `'...'` 内联引文 span，逐个对 OCR 段落匹配。
3. **专用 `evidence_quote` 字段**：`physics_defense` 有专门的逐字证据字段，按省略号 `...` 切片后逐片段匹配。
4. **纠正后提示词产物（模拟）**：从 OCR 段落取 12-18 词逐字片段，模拟"提示词要求产出短逐字引文"时的命中率。

匹配判定（窗口滑动 ratio，解决"短引文嵌入长段落"低分问题）：
- `matched`：精确子串命中，或滑动窗口 ratio ≥ 0.85
- `broken`：0.60 ≤ ratio < 0.85（段落漂移，可重绑）
- `unmatched`：ratio < 0.60（无对应锚点）

## 实验数据

| 子测试 | 命中 | 漂移 | 无锚点 | 命中率 |
|---|---|---|---|---|
| A. 正控制组（OCR 原文截断） | 5 | 0 | 0 | **100%** |
| B. 当前提示词内联引文 | 2 | 0 | 1 | **66.7%**（2/3 可引用字段） |
| C. 专用 `evidence_quote` 字段（切片后） | 11 | 1 | 0 | **91.7%**（11/12 片段） |
| D. 纠正后提示词（模拟短逐字片段） | 60 | 0 | 0 | **100%** |

**最关键的一行数字**：在 8 个 derived JSON 共 **46 个字符串字段**里，**44 个字段根本不包含任何逐字引文**（`no_quote`）。只有 `cyber_attacks.attack_target`（2 条内联引文）和 `physics_defense.evidence_quote_for_physics_use`（专用字段）产出了可锚定的文本。其余 44 个字段——攻击类型、影响、检测方法、代理模型、元数据——全是 LLM 转述或结构化分类，无逐字原文。

## 决定性发现

### 发现 1：承重假设在当前提示词下不成立——但修复成本极低

44/46 字段没有可锚定的逐字引文。这意味着：**用当前 derived JSON 直接投影到锚点表，95.6% 的字段会落到 `no_quote`，无法回答"哪一段"**。同行评审员的"最弱链接"和 `tech-debt-analyst` 的 #1 条件都是对的，综合计划删掉这个条件是错的。

但子测试 D 证明：只要提示词要求产出 ≤18 词的逐字片段，命中率立刻回到 100%。这是一个**提示词层修改**，不动架构，不增加 LLM 调用次数（只是给现有提取加一个约束字段），零额外成本。

### 发现 2：专用证据字段比内联引文更可靠

子测试 C 显示，`evidence_quote_for_physics_use` 这种**独立专用字段**（而非埋在转述句里的内联引文）切片后命中 11/12 = 91.7%。唯一漂移片段是 gemini 把原文 `[equations 9-12]` 改写成"i.e., [equations 9-12]"（ratio 0.69），属于 LLM 的轻度改写，非 OCR 漂移。

结论：**纠正提示词的正确形态不是"在转述里夹引号"，而是"为每个 claim 增加一个独立的逐字证据字段"**。这恰好是 `litrev-extract` 已经在 `physics_defense` 里做过的——只是没在其余 3 个 prompt 里推广。

### 发现 3：OCR 不是瓶颈，提示词才是

子测试 A（100%）和 D（100%）证明：OCR 文本本身足够稳定，逐字片段能 100% 回锚。这与 Phase 0 结论（正文漂移 <5%，全部 ratio ≥0.95）一致。用户的判断"现在的 OCR 准确性是很高的了"被两个独立实验确认。

唯一一个 `unmatched`（子测试 B 第 3 条，ratio 0.31）是 gemini 在 `defense_mechanism_description` 转述里夹了一句残缺引文"s laws and AC power equations"，这是 LLM 截断/改写，不是 OCR 问题。

## 对综合计划的修正

综合简报 Phase 1 的 SQLite `claims` 表 schema 里，`quote` 字段标注"verbatim supporting quote, from derived JSON"。本实验证明：

1. **当前 derived JSON 不满足这个 schema 的前置条件**——95.6% 的字段没有 verbatim quote。直接 ingest 会得到一个 `quote` 列大半为空/`no_quote` 的锚点表。
2. **修复必须在 Phase 1 之前**，作为 Phase 1 的第 0 步：修改 4 个 prompt 模板，为每个 claim 组增加一个 `evidence_quote` 字段，约束为"原文逐字片段，≤18 词，可含省略号连接多个片段"。然后回填这两篇论文的 derived JSON。
3. 这把综合计划里被删掉的 `tech-debt-analyst` #1 条件**显式补回**：提取时必须产出锚点——不是靠 LLM 重读，是靠 prompt 约束。

**修正后的 Phase 1 入口**：不是直接 `know ingest`，而是先 `litrev-extract` 用改过的 prompt 重跑（或仅回填 `evidence_quote` 字段），再 ingest。这仍属"零额外 LLM 成本"——改 prompt 不增加调用次数，只是给每次调用的输出加一个字段。
